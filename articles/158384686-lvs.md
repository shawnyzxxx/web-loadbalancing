## 一、LVS 核心概念与架构

LVS（Linux Virtual Server）是由章文嵩博士开发的高性能负载均衡技术，通过内核层实现流量分发，提升并发处理能力与系统可用性。其核心组件包括：

- **Virtual Server（VS）**：调度器，负责接收客户端请求并转发至真实服务器（RS）。
- **Real Server（RS）**：实际处理请求的后端服务器。
- **VIP（Virtual IP）**：对外暴露的统一访问 IP，用于隐藏后端 RS 的真实地址。
- **DIP（Director IP）**：VS 的内网接口 IP，用于与 RS 通信。
- **RIP（Real Server IP）**：RS 的公网/私网 IP。

典型访问流程：

```text
Client <--> VIP == DIP <--> RIP
```

客户端请求通过 VIP 到达 VS，VS 根据调度策略选择 RS 返回响应，最终数据包直接返回客户端。

## 二、集群与分布式技术对比

LVS 属于集群技术范畴，需要与分布式技术区分：

| 特性 | 集群 | 分布式 |
| --- | --- | --- |
| 功能一致性 | 所有节点功能相同 | 节点分工协作 |
| 数据一致性 | 完全同步 | 按需拆分 |
| 扩展方式 | 向上扩展（Scale Up） | 向外扩展（Scale Out） |
| 容错机制 | 高可用（HA） | 任务拆分冗余 |

与 SLA 相关的核心指标：

> MTBF（平均无故障时间）+ MTTR（平均恢复时间）→ A = MTBF / (MTBF + MTTR)，例如目标达成率为 99.9%。

## 三、LVS 工作模式解析

LVS 支持四种转发模式，适用于不同的网络拓扑：

### 1. NAT 模式

- **特点**：修改报文目标 IP（DNAT），RS 的网关指向 DIP。
- **优势**：兼容性强，支持端口映射。
- **缺点**：VS 易成为瓶颈，需清理 iptables 规则。

### 2. DR 模式（直接路由）

- **特点**：封装 MAC 首部，由 RS 直接响应客户端。
- **优势**：低延迟，适合跨网络场景。
- **配置要点**：在 RS 上限制 ARP 通告。


```bash
# RS 上限制 ARP 通告
echo "1" > /proc/sys/net/ipv4/conf/all/arp_ignore
echo "2" > /proc/sys/net/ipv4/conf/all/arp_announce
```

### 3. TUN 模式（隧道模式）

- **特点**：外层封装 IP 头，支持远距离通信。
- **限制**：RS 需支持隧道协议，不支持端口映射。

### 4. FULLNAT 模式

- **特点**：同时修改源/目标 IP，需要公网地址。
- **注意**：默认内核未启用，需要特殊编译支持。

## 四、调度算法与性能优化

LVS 提供多种调度策略，分为静态与动态两类：

### 静态算法

- **轮询（RR）**：均匀分配请求，适合同构 RS。
- **加权轮询（WRR）**：按权重分配，性能差的节点减少调度次数。
- **源哈希（SH）**：会话保持，同一客户端固定分配到同一 RS。
- **目标哈希（DH）**：按目标地址分配，适用于代理缓存场景。

### 动态算法

- **最少连接（LC）**：优先选择活动连接数少的 RS。
- **带权最少连接（WLC）**：结合权重计算负载值。
- **最短期望延迟（SED）**：初始高权重优先，后续按负载调整。
- **灰度发布（FO）**：标记过载 RS，避免调度到该节点。

### 实战案例：权重调度配置

添加一个权重比为 2:1 的调度服务：


```bash
ipvsadm -A -t 172.25.254.100:80 -s wrr
ipvsadm -a -t 172.25.254.100:80 -r 192.168.0.101:80 -m -w 2
ipvsadm -a -t 172.25.254.100:80 -r 192.168.0.102:80 -m -w 1
```

## 五、高级功能与常见问题

### 1. 防火墙标记（FWM）解决轮询冲突

**场景**：同一台真实服务器（RS）开放多个端口（如 HTTP 80 / HTTPS 443）时，需要避免跨端口请求被分配到不同的服务器，否则会导致负载不均。

**实现原理**：通过 `iptables` 对目标端口打上标记（MARK），再绑定到统一的调度服务（Firewall Mark，FWM）。


```bash
# 对访问 VIP 的 HTTP/HTTPS 请求打标记
iptables -t mangle -A PREROUTING \
  -d $VIP -p tcp --dports 80,443 \
  -j MARK --set-mark 6666

# 创建基于标记的调度规则（加权轮询）
ipvsadm -A -f 6666 -s wrr
ipvsadm -a -f 6666 -r rs1:80 -g -w 2
ipvsadm -a -f 6666 -r rs2:80 -g -w 1
```

### 2. 持久连接（Sticky Session）

**原理**：通过 `ipvsadm` 的 `-p` 参数记录客户端 IP 与后端服务器的映射关系，超时后重置关联。


```bash
# 为标记 6666 的服务启用持久化（300 秒）
ipvsadm -E -f 6666 -s wrr -p 3000
```

### 7. 规则持久化

以上操作都是临时生效的，下面让规则永久生效。

**方式一：利用自定义文件持久化**


```bash
[root@vsnode ~]# ipvsadm-save -n
-A -t 172.25.254.100:80 -s wrr
-a -t 172.25.254.100:80 -r 192.168.0.10:80 -m -w 2
-a -t 172.25.254.100:80 -r 192.168.0.20:80 -m -w 1
[root@vsnode ~]# ipvsadm-save -n > /mnt/ipvs.rule
[root@vsnode ~]# ipvsadm -C
[root@vsnode ~]# ipvsadm-restore < /mnt/ipvs.rule
```

**方式二：利用守护进程持久化**


```bash
[root@vsnode ~]# ipvsadm-save -n > /etc/sysconfig/ipvsadm
[root@vsnode ~]# ipvsadm -C
[root@vsnode ~]# systemctl enable --now ipvsadm.service
Created symlink /etc/systemd/system/multi-user.target.wants/ipvsadm.service -> /usr/lib/systemd/system/ipvsadm.service.
```

## 八、轮询调度问题与 FWM 解决方案

### 1. 问题现象

以 HTTP 和 HTTPS 为例：当在 RS 中同时开放 80 和 443 端口时，默认是分开轮询的，会出现轮询错乱。例如第一次访问 80 被轮询到 RS1 后，下次访问 443 仍可能被轮询到 RS1 上。

### 2. 复现问题

需要在服务器 RS1 和 RS2 上配置 HTTPS 服务：

```bash
[root@RS1 system-connections]# yum install mod_ssl -y
[root@RS1 system-connections]# systemctl restart httpd
```

在 vsnode 上分别对 80 和 443 配置轮询策略：

```bash
[root@vsnode ~]# ipvsadm -A -t 192.168.0.200:80 -s rr
[root@vsnode ~]# ipvsadm -A -t 192.168.0.200:443 -s rr
[root@vsnode ~]# ipvsadm -a -t 192.168.0.200:80 -r 192.168.0.10:80 -g
[root@vsnode ~]# ipvsadm -a -t 192.168.0.200:80 -r 192.168.0.20:80 -g
[root@vsnode ~]# ipvsadm -a -t 192.168.0.200:443 -r 192.168.0.10:80 -g
[root@vsnode ~]# ipvsadm -a -t 192.168.0.200:443 -r 192.168.0.20:80 -g
[root@vsnode ~]# ipvsadm -Ln
IP Virtual Server version 1.2.1 (size=4096)
Prot LocalAddress:Port Scheduler Flags
  -> RemoteAddress:Port           Forward Weight ActiveConn InActConn
TCP  192.168.0.200:80 rr
  -> 192.168.0.10:80              Route   1      0          0
  -> 192.168.0.20:80              Route   1      0          0
TCP  192.168.0.200:443 rr
  -> 192.168.0.10:443             Route   1      0          0
  -> 192.168.0.20:443             Route   1      0          0
```

测试：

```bash
[root@client ~]# curl http://192.168.0.200;curl -k https://192.168.0.200
RS2 - 192.168.0.20
RS2 - 192.168.0.20
```

两次访问都被调度到同一台服务器上，下面给出解决方法。

### 3. 使用防火墙标记解决

防火墙标记（Firewall Mark）允许管理员给特定的数据包打上一个数字“标签”。LVS 的持久性连接机制不仅可以基于单个连接，还可以基于这个标记来保持会话：将多个不同的连接标记为同一个值后，LVS 会把这些连接看作同一个“会话”的一部分，从而将它们定向到同一台真实服务器。

工作流程：

**（1）用户首次访问 `http://VIP`（端口 80）：**

1. 数据包到达 Director，进入 PREROUTING 链。
2. iptables 规则匹配目标端口 80，给数据包设置标记 10。
3. LVS 检查这个标记为 10 的连接是否已有持久化记录。
4. 因为是首次访问，没有记录，LVS 根据调度算法（如 WLC）选择一台 RS（例如 RS1），并在持久化表中建立记录：“客户 IP + 标记 10” → RS1。
5. 数据包被转发给 RS1。

**（2）同一用户随后访问 `https://VIP`（端口 443）：**

1. 数据包到达 Director，进入 PREROUTING 链。
2. iptables 规则匹配目标端口 443，给数据包设置标记 10。
3. LVS 检查标记为 10 的连接，发现该客户 IP 已有持久化记录指向 RS1。
4. LVS 不经过调度算法，直接根据持久化记录将数据包转发给 RS1。

**（3）访问 `http://VIP:8080`：**

过程同上，因为标记同样是 10，所以请求依然被发往 RS1。

在 vsnode 上配置基于标记的调度：

```bash
[root@vsnode ~]# ipvsadm -A -f 6666 -s rr
[root@vsnode ~]# ipvsadm -a -f 6666 -r 192.168.0.10 -g
[root@vsnode ~]# ipvsadm -a -f 6666 -r 192.168.0.20 -g
[root@vsnode ~]# ipvsadm -Ln
IP Virtual Server version 1.2.1 (size=4096)
Prot LocalAddress:Port Scheduler Flags
  -> RemoteAddress:Port           Forward Weight ActiveConn InActConn
TCP  192.168.0.200:80 rr
  -> 192.168.0.10:80              Route   1      0          1
  -> 192.168.0.20:80              Route   1      0          0
TCP  192.168.0.200:443 rr
  -> 192.168.0.10:443             Route   1      0          0
  -> 192.168.0.20:443             Route   1      0          0
FWM  6666 rr
  -> 192.168.0.10:0               Route   1      0          0
  -> 192.168.0.20:0               Route   1      0          0
```

测试：

```bash
[root@client ~]# curl -k https://192.168.0.200
RS1 - 192.168.0.10
[root@client ~]# curl -k https://192.168.0.200
RS2 - 192.168.0.20
[root@client ~]# curl -k https://192.168.0.200
RS1 - 192.168.0.10
[root@client ~]# curl -k https://192.168.0.200;curl 192.168.0.200
RS2 - 192.168.0.20
RS1 - 192.168.0.10
```

这样就使用防火墙标记解决了轮询规则中可能遇到的错误。

## 九、LVS 工作模式总结

至此，LVS 的 NAT 与 DR 模式部署均已介绍完毕，两种模式对比如下：

| 对比项 | NAT 模式 | DR 模式 |
| --- | --- | --- |
| RS 操作系统 | 不限 | 禁用 arp |
| 调度器和服务器网络 | 可跨网络 | 不可跨网络 |
| 调度服务器数量与服务器数量 | 少 | 多 |
| RS 服务器网关 | 指向调度器 DIP | 指向路由 |

补充说明：

- **lvs-nat 与 lvs-fullnat**：请求和响应报文都经由 Director。
- **lvs-nat**：RIP 的网关要指向 DIP。
- **lvs-fullnat**：RIP 和 DIP 未必在同一 IP 网络，但要能通信。
- **lvs-dr**：通过封装新的 MAC 首部实现，通过 MAC 网络转发。
